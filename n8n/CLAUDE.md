# n8n – оркестрация Video Digest

Здесь живут флоу n8n (экспорт в json), промпты LLM-этапов и скрипты для синхронизации с инстансом.

## Инстанс
- Локальный n8n из `../infra/docker-compose.yml`, `http://localhost:5678`. Боевого инстанса нет, других флоу там нет – это единственное место, где ты работаешь.
- Доступ через REST API n8n, ключ – `N8N_API_KEY` из `../infra/.env`. Ключи из `.env` никогда не попадают в код, промпты, json флоу и коммиты.
- Media Service из compose (`http://media:8000` внутри сети, `http://localhost:8000` снаружи), ключ `MEDIA_API_KEY`. Его API – `../media-service/README.md`.
- Postgres из compose, таблица `jobs` создаётся из `../infra/sql/001_jobs.sql`.

## Источник правды
- `../docs/contract-api.md` – какие ручки, какие статусы, порядок этапов пайплайна. Это главный документ для этой папки.
- `../docs/result-schema.md` – что лежит в `jobs.result`. Схема неизменяема без правки документа.
- `../docs/TZ-media-service.md` – только для понимания, что умеет медиа-сервис.

## Структура папки
```
n8n/
  workflows/        # экспорт флоу: jobs-api, pipeline, llm-call, log-events, maintenance, on-error (Error Workflow пайплайна)
  prompts/          # промпты по одному на этап, см. ниже
  fixtures/         # пример результата по схеме, тестовые ответы; clean-calibration/ – записанные вызовы clean для харнесса
  testing/          # provider-stub.json – заглушка провайдеров для проверки транспортного повтора (в инстансе выключена, в экспорт не попадает)
  scripts/          # export.sh, import.sh – синхронизация; validator_harness.js, fetch_job_executions.sh – проверка валидатора на записях; clean_retention.js – измеритель удержания, clean_retention_report.js – его калибровка на записях; transport_retry.js – вердикт транспортного повтора
  CLAUDE.md
```

## Как работаем
- Флоу строятся через API и сразу экспортируются в `workflows/*.json`. Состояние в инстансе и в репо не должно расходиться: после каждого шага – экспорт и коммит.
- `scripts/build_workflows.py` – инструмент разработки: генерирует `workflows/*.json` из Python. Источник правды – экспорт из инстанса (`scripts/export.sh`), не генератор: после генерации – `import.sh`, затем `export.sh`, коммитится результат экспорта.
- Шаг в n8n не закрыт, пока после `import.sh` и `export.sh` пересборка генератором не даёт пустой diff к экспорту по всем флоу (шесть с 21 сентября), а не только по правленым: 20 сентября правка `Clean done` три дня лежала в генераторе, не дойдя до инстанса, при отчёте «работает».
- В `fixtures/` попадают только публичные записи наших собственных прогонов; ничего принесённого пользователем туда не кладём.
- В экспорте не должно быть credentials, ключей, локальных id. Скрипт экспорта это вычищает.
- Промпты – отдельные файлы в `prompts/`, на английском, с явным требованием к языку вывода. В нодах n8n промпт читается из файла (папка монтируется в контейнер), не дублируется текстом внутри ноды.
- Любая правка валидатора llm-call сначала гоняется на записанных ответах моделей: `scripts/validator_harness.js` (см. `scripts/validator-harness.md`), без модели и без оплаты; в инстанс – только после этого.
- Каждый LLM-вызов возвращает JSON, который проверяется по схеме (п. 9 `result-schema.md`) до записи в базу. Повторная попытка при невалидном ответе – одна: отклонённый ответ возвращается модели вместе с текстом ошибки, чтобы она исправила названное поле и сохранила остальное.
- Стоимость и время каждого этапа пишутся в `jobs.meta.stages` с первого дня, даже для фейкового пайплайна.
- Если для работы нужно изменить `../infra/docker-compose.yml` (монтирование `prompts/`, переменные n8n вроде `N8N_BLOCK_ENV_ACCESS_IN_NODE`), правь только сервис `n8n` и опиши изменение в отчёте.
- Порядок реализации – п. 8 контракта. Шаг за шагом, показать, ждать «ок», отдельный коммит.
- Общение – по-русски, промпты и комментарии в Code-нодах – по-английски.
